# Approved feed directory replacement

## Approved automated employer profiles · 5 November 2026

The requested rollout uses the approved Wildmere layout, AI research from official sources and automatic publication. The user explicitly approved this data model and rollout on 5 November 2026.

1. **Store one profile per verified organisation in WildJobs Supabase.** Add an `employer_profiles` table keyed to `directory_organisations.name`, with a unique stable slug, the verified website, published profile content with a citation URL for each claim, and the research date. Store retry times, worker leases and failure reasons separately from public content access. Anonymous visitors can read only current published profiles. Only the existing automation service can claim or write research. Add an index on canonical vacancies by organisation and posting date. Existing employer and job records remain in place.
2. **Research official sources in the background.** Start with the employer websites already linked from directory listings. Confirm the site identifies the hiring organisation, then read a bounded set of official About, Projects and Careers pages. Follow links within the verified site, use the existing network protections, respect crawl restrictions and retry temporary failures. Submit bounded text to the existing OpenAI integration. Ask for UK English summaries, supporting excerpts and source IDs. Treat page content as untrusted data, check that each excerpt occurs in the cited page, and check that the summary follows from it before publishing. Keep source links and check dates with the public copy. Omit employment claims unless the official careers material supports them and preserves any role-specific qualification.
3. **Publish automatically once the evidence is useful.** Require a verified identity and enough distinct evidence for a factual overview and at least one concrete project or area of work, drawn from at least two official pages. Leave the job search link in place if the identity is uncertain, evidence is too thin, or an employer has no verified site. Run a bounded number of profiles per heartbeat, with a lease so overlapping requests cannot repeat the same paid work. Recheck successful profiles every 90 days, retry sparse evidence after two weeks and back off on temporary errors. Withdraw stale content after 180 days without verification and withdraw it sooner if the employer identity changes. No manual review queue.
4. **Connect the page to WildJobs data.** Use `/employers/<slug>`, surface it from the employer directory and job cards, and include eligible pages in the sitemap under the existing indexing switch. Keep published profiles available between hiring rounds. Use the homepage cards and existing expiry rules for live roles, and match up to three guides by role and category. Add hiring observations from deduplicated WildJobs adverts, with dates and sample sizes. Show salary only where the existing comparability rules support it. Select a relevant credited image from the existing Unsplash collection when there is a good match. Use a simple header when there is no match.
5. **Release in stages.** Verify the new read and write rules against a test database. Deploy the application and additive migration with research switched off. Run a bounded initial production batch, verify the resulting source links, current roles and sitemap behavior, then enable the existing heartbeat to continue processing. Unpublish individual profiles or pause further research if a problem appears. This is release verification, with ongoing profile publication governed by the automatic checks above.

For a concrete example, WildJobs already associates RSPB with its official site. Its [organisation overview](https://www.rspb.org.uk/about-us/who-we-are) supports a factual mission summary, and its [UK conservation work](https://www.rspb.org.uk/helping-nature/what-we-do/protecting-species-and-habitats/conservation-in-the-uk) gives a concrete example in the Welsh Rainforest restoration project. Its [careers information](https://www.rspb.org.uk/careers/what-we-offer) supports saying that flexible arrangements may be available depending on the role. Live vacancies would come from WildJobs.

The full rollout covers every named directory employer, including organisations between hiring rounds. When a verified website is missing, the worker checks up to two original adverts, then runs a bounded web search if needed. A cited candidate must identify the exact employer on its own website before WildJobs records it. Discovery and profile research use separate scheduled attempts. Each profile still has to meet the official evidence threshold before publication.

## International salaries

Salary parsing is shared by feed fields, linked adverts, AI output and public cards. Preserve original pay and its stated period; use explicit ISO currency codes for currencies other than GBP (£) and EUR (€). Bare $ and ¥ remain ambiguous unless the source supplies a currency. Do not convert currencies or annualise hourly, monthly or fortnightly pay. Description extraction looks for pay wording, excluding nearby budgets, expenses and awards. The existing minimum-salary filter is labelled GBP and matches confirmed annual GBP minimums only; international jobs remain visible without that filter. Existing salary text and numeric columns suffice; no migration, extra service or additional AI call is needed.

Malformed salary units in advert metadata fall back to the matching amount in visible advert text or the RSS pay header. Explicit advertised currencies can clarify bare symbols without overriding stated pay periods.

## Employer branding

Reuse `directory_organisations.logo_url` across an employer’s listings. The existing AI pass chooses an official employer website when no logo is available, using advert links and business email domains as candidates. Normal importer code fetches and checks the employer site and a real logo image; AI never generates logos or guesses image URLs. Simple inline brand SVGs can also be cached. If an advert-linked site blocks the read or its declared images fail, fetch its branded website icon through Google’s public favicon endpoint and embed the image in the cached logo value. Visitors do not request that icon service. Missing-icon responses and generic platform favicons are rejected. Lookups are deduplicated within each batch, bounded in time, and failures leave the existing card fallback without holding publication. The admin logo override remains available.
