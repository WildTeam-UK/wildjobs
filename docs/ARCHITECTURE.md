# WildJobs architecture

The listing lifecycle, field dictionary, enrichment boundaries and publication gates are defined in [LISTING_PIPELINE.md](./LISTING_PIPELINE.md). That document takes precedence over earlier automation descriptions in this file where they conflict.

## Current implementation

WildJobs is a Next.js App Router application written in strict TypeScript and independently deployed on Vercel. Public job and employer pages, candidate authentication, private saved jobs, explicit preferences, audited staff publication and closure actions, and the controlled employer-submission journey are connected to the independent WildJobs Supabase project. Invitation tokens are generated by a staff-only Server Action, stored only as SHA-256 hashes and displayed once for copying. A protected same-origin Route Handler validates complete employer submissions, and an atomic database function both creates the private review record and consumes the invitation. Course filters and job matches read reviewed Supabase capability mappings. The server-side LearnWorlds catalogue sync is implemented but remains inactive until its credentials and approved-course allowlist are configured.

```text
browser
  -> Next.js server-rendered public pages
       -> Supabase public job catalogue protected by Row Level Security
       -> Supabase Auth for candidate and staff sessions
       -> authenticated staff review, publication and closure actions
       -> staff-only creation of hashed, seven-day submission invitations
       -> protected invitation redemption into the private submission queue
       -> administrator-triggered and protected scheduled source discovery
       -> allowlisted LearnWorlds public course catalogue sync every six hours when configured
       -> bounded vacancy and employer enrichment with field-level evidence
       -> shadow or live automatic-publication decisions with exact blocker reasons
  -> no optional analytics or marketing integration
```

## Beta architecture

```text
browser
  -> Vercel CDN and Next.js application
       -> server-rendered job discovery pages
       -> Server Actions for approved staff writes
       -> separate WildJobs Supabase project
            -> Postgres
            -> Row Level Security
            -> candidate and staff Supabase Auth
       -> exact-host source adapters
            -> WWT public vacancies HTML
            -> Countryside Jobs Service RSS 2.0
            -> public vacancy identities and content hashes only
            -> private discovery queue
            -> approved vacancy-page fetch and canonical employer matching
            -> deterministic extraction, then optional evidence-bound AI extraction
            -> evidence, duplicate, date and employer-profile publication policy
            -> atomic automatic publication when live mode is explicitly enabled
            -> staff exception review for every blocked record
       -> LearnWorlds API v2, server-side read access only
            -> allowlisted public course metadata
            -> no learner, enrolment, purchase, progress or certificate requests
```

The first production backend should use normal request-driven Vercel Functions. Do not introduce Services, Queues or durable Workflows until workload evidence requires them.

## Application ownership

- WildJobs owns job, employer and future career-profile records.
- LearnWorlds owns learner accounts, purchases, progress, certificates and training access.
- Brevo owns marketing subscription preferences and consent evidence.
- `wildteam-shared` owns shared standards, design tokens and reusable UI packages.
- WildNews remains operationally and technically independent.

## Shared packages

Do not commit a sibling `file:` dependency. During package development, temporary local linking may be used without changing `package.json`. WildJobs pins deliberate private package versions from GitHub Packages and upgrades them through its own reviewed changes.

`@wildteam-uk/tokens` is the source of truth for shared `--wt-*` values. GitHub Actions reads the package with its repository-scoped workflow token. Local developers authenticate through their personal npm configuration; credentials are never committed. Before the first Vercel preview, configure a read-only package token in Vercel's secret environment without exposing it to application runtime code.

## Database boundary

The independent `wildjobs` Supabase project and beta schema were created in the WildTeam UK organisation on 2026-10-28. The application reads and writes the hosted database through authenticated, RLS-protected clients; no service-role key is exposed to the browser.

The schema includes employers, jobs, career areas, course-capability mappings, provenance, import runs, controlled employer submissions, candidate profiles, saved jobs, preferences and staff moderation. All changes remain ordered migrations in `supabase/migrations`.

The LearnWorlds integration is owned by WildJobs for this beta use case and uses a server-only access token plus
client ID against the school-specific version 2 API URL. Its data category is public course catalogue metadata:
stable identifier, title, public description, URL and availability. An environment allowlist is the operational
approval boundary. The sync never requests learner endpoints. Failures keep the last reviewed catalogue intact,
record only a constrained error code and retry on a later six-hour claim. Removing an allowlisted course from the
provider response makes an existing WildJobs course inactive; it does not delete or alter the LearnWorlds record.
WildJobs retains the catalogue copy while its capability mapping is in use and can archive or delete that copy
independently when the mapping is retired. After a changed catalogue sync, a bounded structured-output pass creates
one to four course-backed capabilities per course, reuses canonical names and aliases first, requires exact summary
evidence and records confidence and policy version. A source hash skips unchanged catalogues; staff-authored records
are never replaced by the generated set.

Every table in an exposed schema has RLS. Public access is limited to active, approved listings. Staff access requires an active staff record. Current connectors permit only reviewed source endpoints. Administrators can run them on demand. Supabase `pg_cron` calls a protected Vercel heartbeat every minute through `pg_net`, using a bearer secret stored in Supabase Vault. An atomic database claim releases source-import work once every two hours. Between imports, each heartbeat may enrich one pending vacancy and record its publication readiness. Once enrichment is idle, the heartbeat refreshes a bounded batch of decisions created under an older publication policy without repeating AI work. Shadow mode can refresh ten decisions per heartbeat; live mode permits only one. The route uses a server-only Supabase secret key, rejects requests without the matching automation secret and prevents overlapping enrichment work. `AUTO_PUBLISH_ENABLED` defaults off, so readiness initially runs in shadow mode.

Enrichment is deliberately bounded. WildJobs fetches only an approved vacancy URL and a maximum of two public HTTPS employer pages protected by private-network and size checks: the official homepage and, when linked, one same-site mission, About or organisation page. Deterministic rules run first. An optional direct OpenAI Responses API structured-output call receives only unresolved fields plus bounded source text, must return exact evidence and cannot estimate salary or assume an on-site role. If a new canonical employer has no known website, that same response may perform one low-context web-search step for the official site. WildJobs rejects job boards, social networks and unsafe URLs, requires the selected page to appear in the returned sources, fetches it through the protected employer-page path and saves a researched fact only when its exact evidence appears on the fetched page. A newly discovered official site with an incomplete profile remains eligible for another bounded pass, but the existing three-attempt record limit remains the absolute ceiling. The server-only `OPENAI_API_KEY` follows the same provider pattern as WildNews. `AI_ENRICHMENT_ENABLED` is the master off-switch; the default is off. Each record receives at most three attempts, every AI call has a timeout and output cap, and daily request/input/output limits stop runaway spend. Every run records token usage and model metadata, and unchanged page content is skipped. Once an employer has enrichment evidence, later vacancies reuse the canonical employer rather than researching it again.

Capability-policy backfills are separate from full enrichment. The heartbeat classifies one already-published job
at a time from its stored trusted source text, updates only source/job capability relationships and policy metadata,
and never rewrites the published job or repeats publication. This pass does not consume another full-enrichment
attempt, but it remains covered by the same daily AI request and token limits.

Automatic publication is a separate, versioned policy. It requires an active feed or API source, no duplicate risk, a secure source or application destination, a canonical employer, a usable title, description and summary, completed enrichment and a valid lifetime. A source-provided closing date is used when available; otherwise the listing expires 30 days after first discovery. Salary, location, workplace, paid/volunteer status, contract, hours, experience and employer profile copy remain valuable enrichment but do not block an otherwise trustworthy vacancy when genuinely unstated. Automation never fabricates them. Every decision records its score, blocker codes and evidence confidences. Only the service role can call the atomic publication function, and every resulting job receives automation-authored moderation events.

Public jobs keep `source_url` and `application_url` separate. The source link preserves where WildJobs found the listing; the application link may point directly to the employer or remain on a job board. Employer profiles use the canonical employer website independently of both.

## Search

Start with Postgres full-text search and appropriate indexes. Do not add a separate search service until query quality, volume or latency demonstrates the need.

## Privacy and measurement

Supabase Auth and candidate-owned records hold the minimum account data required for enabled account features. The application loads no optional analytics. Alerts, marketing integration and cross-application measurement require separate privacy and consent review.

## Environments

Local, preview and production environments must remain distinct. Environment-variable names and purposes will be documented in `.env.example` when the first external service is approved. Real values are never committed.
